# sqlite-mcp-server

A [Model Context Protocol](https://modelcontextprotocol.io) server that gives an AI agent
read-only access to a local SQLite database. Ask a connected agent "which city spends the
most on books?" and it explores the schema, writes the SQL, runs it here and answers.

It's built on the **official MCP Python SDK** (`mcp`, the `FastMCP` high-level API). The
SDK handles the protocol plumbing; this project focuses on exposing a SQLite database as
tools and resources and on running the model's SQL safely.

```
 Agent host / IDE / Inspector   (the MCP client, which owns the LLM)
          |  stdin/stdout pipes
          v
 the MCP SDK (FastMCP)   JSON-RPC 2.0, stdio, the initialize handshake,
                         capabilities, tools/resources/prompts dispatch
          |
          v
 server.py      our tools, resource template and prompt
 database.py    read-only, sandboxed query execution
          |
          v
      bookstore.db
```

## Where the "natural language" actually happens

Not here. The server never sees an English question it has to interpret. The client's
model reads the tool descriptions and schema, calls `list_tables` and `describe_table`,
writes SQL itself and sends it to `run_query`. The server's two jobs are to make that easy
(clear descriptions, schema on demand, errors the model can learn from) and to make it safe
(the model's SQL is untrusted input).

## What the SDK does, and what this project does

| The SDK (`FastMCP`) handles | This project owns |
| --- | --- |
| JSON-RPC 2.0 framing and error codes | the three SQLite tools |
| the stdio transport | the schema resource + per-table template |
| the `initialize` handshake and capability negotiation | the `ask_database` prompt |
| `tools/list`, `tools/call`, resources, prompts dispatch | **the read-only safety model** (`database.py`) |
| generating each tool's JSON Schema from type hints | the sample database |
| turning an exception in a tool into `isError: true` | |

The one thing the SDK does **not** do is keep the model's SQL safe — that's the interesting
part and it's all in `database.py`.

## Quick start

Requires Python 3.10+.

```bash
git clone https://github.com/sreekant2x/sqlite-mcp-server
cd sqlite-mcp-server
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

python -m sqlite_mcp.sample_data bookstore.db   # build the sample database
python scripts/raw_client.py bookstore.db       # watch a session on the wire
pytest                                          # run the tests
```

### Use it from a desktop MCP client

Add this to your client's MCP config file (for example `claude_desktop_config.json`), with
absolute paths:

```json
{
  "mcpServers": {
    "bookstore": {
      "command": "/absolute/path/to/sqlite-mcp-server/.venv/bin/python",
      "args": ["-m", "sqlite_mcp", "/absolute/path/to/bookstore.db"]
    }
  }
}
```

Restart the client and ask "Which author has earned the most revenue, and from which book?"

### Inspect it with the MCP Inspector

```bash
npx @modelcontextprotocol/inspector .venv/bin/python -m sqlite_mcp bookstore.db
```

## What the server exposes (`server.py`)

Three primitives, split by who decides to use them:

| Primitive | Controlled by | Here |
| --- | --- | --- |
| Tools | the model | `list_tables`, `describe_table`, `run_query` |
| Resources | the application | `sqlite://schema`, `sqlite://table/{table}` |
| Prompts | the user | `ask_database` |

Each tool's argument schema is generated by the SDK from the function's type hints and
`pydantic.Field` annotations — for example `run_query`'s `limit` is advertised as an integer
between 1 and 1000.

## The read-only safety model (`database.py`)

The model writes the SQL, so every query is untrusted. Defence in depth:

1. The file is opened with SQLite's `mode=ro` URI flag, and `PRAGMA query_only` is on.
2. While a model-written query runs, an **authorizer callback** allows only `SELECT`, column
   reads and function calls (minus `load_extension`). SQLite asks the authorizer about every
   action in the *parsed* statement, so `INSERT`, `DROP`, `ATTACH`, `PRAGMA` and
   `WITH x AS (...) DELETE ...` are all refused before they run. A regex like "starts with
   SELECT" can't tell what a statement does; the parser can.
3. Python's `sqlite3` refuses to run more than one statement per call, so
   `SELECT 1; DROP TABLE books` fails outright.
4. A progress handler aborts any query running past a deadline (5 s by default).
5. Results are capped (100 rows by default, 1000 max) with a `truncated` flag.

A refused query is raised as an exception, which the SDK returns to the model as a tool
result with `isError: true` — so the model reads the message and can retry, instead of the
client swallowing a protocol error.

> **Python 3.10 note:** removing a SQLite authorizer with `set_authorizer(None)` needs
> Python 3.11+. So the authorizer is installed once and gated by a flag that's only on
> during model-written queries (`database.py`).

## Tests

```bash
pytest
```

- `test_database.py`: the read-only guarantees, called directly. Each attack
  (`DELETE`, `DROP`, `ATTACH`, stacked statements, a runaway recursive CTE) is thrown at the
  server and the database file's hash is checked unchanged afterward.
- `test_server.py`: the SDK's own client drives the real `python -m sqlite_mcp` process over
  stdio through a full session — initialize, `tools/list`, every tool, resources and the
  prompt — and confirms writes come back as `isError: true` and leave the file unchanged.

## What this deliberately leaves out

- **Access control below the table level.** Anyone who can query can read any row.
- **Streamable HTTP transport** and authentication (the SDK supports it; this server runs
  over stdio only).
- **Concurrency.** Requests are handled one at a time.
